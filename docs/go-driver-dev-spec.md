# Go 司机端后端开发规范

## 1. 适用范围

本文档适用于 `taketaxi` 司机端后端服务开发，覆盖以下工程：

- `taketaxi/bffDriver`
- `taketaxi/srvDriver`
- 与司机端直接相关的公共包、配置、脚本与协议定义

本文档用于约束新功能开发、代码评审、缺陷修复与存量代码治理。

规则按以下级别定义：

- `必须`：所有新代码必须满足，存量代码在改动触达时必须逐步整改
- `禁止`：任何新代码不得出现，存量代码发现后应列入整改范围
- `推荐`：鼓励遵循，在不破坏交付节奏前提下优先执行

## 2. 目标

- 保证 `bffDriver` 与 `srvDriver` 的职责清晰
- 保证司机端个人中心及相关模块具备可维护性、可测试性、可扩展性
- 降低接口语义混乱、状态失控、日志不可追踪、错误难排查等问题
- 为后续模块复制提供统一模板

## 3. 分层与目录职责

### 3.1 总体分层

司机端服务按以下职责分层：

1. `BFF`：面向端能力编排、协议转换、登录态校验、聚合返回
2. `Service`：业务规则、状态流转、事务控制、幂等控制
3. `Repository`：数据库读写与持久化细节封装
4. `Model`：数据库实体、领域对象、通用响应结构
5. `RPC Client`：调用下游服务的客户端封装

### 3.2 目录职责

#### `taketaxi/bffDriver`

- `cmd`：进程启动、依赖装配、配置加载
- `internal/router`：路由注册，不写业务逻辑
- `internal/middleware`：鉴权、日志、恢复、链路信息透传
- `internal/handler`：HTTP 入参解析、参数校验、调用 RPC、组装响应
- `internal/rpcClient`：访问 `srvDriver` 或其他服务的客户端包装

#### `taketaxi/srvDriver`

- `cmd`：服务启动、依赖注入、配置装配
- `internal/handler`：gRPC Handler 或服务入口层，负责协议转换与基础校验
- `internal/service`：业务逻辑核心层
- `internal/repository`：数据库访问层
- `internal/model`：实体、查询对象、结果对象、枚举和值对象

### 3.3 分层规则

#### 必须

- `handler` 只能依赖 `service`，不能直接操作数据库
- `service` 只能通过 `repository` 访问持久化层，不能直接拼 SQL 到业务流程中
- `repository` 只负责数据存取，不承载业务规则判断
- `bffDriver` 只处理端侧语义与聚合逻辑，不重复实现 `srvDriver` 中的核心业务规则
- 每层输入输出都必须使用清晰的数据结构，不允许多层直接透传 `map[string]any`

#### 禁止

- 禁止在 `handler` 中写事务逻辑
- 禁止在 `repository` 中写鉴权、风控、状态机判断
- 禁止跨层反向依赖，例如 `repository` 依赖 `handler`
- 禁止为了“省事”在多个层之间复用同一个结构体承担请求、数据库实体、响应三个角色

#### 推荐

- 按业务域拆分文件，例如 `profile`、`wallet`、`verify`、`bankcard`
- 单个文件尽量只承载一个核心职责，超过 300 到 500 行应评估拆分
- 新增业务时优先延续现有分层，不引入额外的“万能 util 层”承接核心逻辑

## 4. 命名规范

### 4.1 包命名

#### 必须

- 包名使用小写英文，采用有业务语义的单词
- 同一层内包名与职责保持一致，如 `service`、`repository`

#### 禁止

- 禁止使用 `common`, `util`, `misc`, `helper2` 这类无明确边界的包名承载核心业务
- 禁止使用拼音缩写或团队内隐语作为包名

### 4.2 文件命名

#### 必须

- 文件名采用小写驼峰或下划线风格，项目内保持一致
- 业务文件名应体现领域与职责，如 `profileService.go`、`walletRepo.go`

#### 禁止

- 禁止使用 `test1.go`、`new.go`、`tmp.go`、`final.go` 这类无语义文件名

### 4.3 类型与方法命名

#### 必须

- 导出类型、接口、方法使用 PascalCase
- 非导出方法使用 camelCase
- 方法名必须体现动作与业务语义，例如 `GetDriverProfile`、`UpdateDriverAvatar`
- 布尔方法优先使用 `Is`、`Has`、`Can` 前缀

#### 禁止

- 禁止出现 `Do`, `HandleData`, `Process`, `CommonQuery` 这类语义过宽的方法名
- 禁止使用 `GetData`, `UpdateInfo` 这类不能体现业务对象的方法名

#### 推荐

- 查询类方法使用 `Get`、`List`、`Find`
- 创建类方法使用 `Create`
- 修改类方法使用 `Update`
- 状态推进类方法使用 `Approve`、`Reject`、`Submit`、`Bind`、`Unbind` 等业务动作词

## 5. 数据结构规范

### 5.1 结构体分层

#### 必须

- 请求结构与响应结构必须独立定义
- 数据库实体必须与接口入参、出参解耦
- 涉及跨服务协议时，优先使用 proto message 作为传输结构，不直接暴露数据库实体

建议采用以下命名：

- `XXXRequest`：入参
- `XXXResponse`：出参
- `XXXDTO`：跨层传输对象
- `XXXDO`：数据库持久化对象
- `XXXVO`：面向前端展示对象
- `XXXQuery`：查询条件对象

#### 禁止

- 禁止将 GORM Model 直接序列化后返回给前端
- 禁止把前端请求结构直接传给 `repository`

### 5.2 字段设计

#### 必须

- 字段名必须表达准确业务含义
- 状态字段必须使用明确枚举值，不允许魔法数字散落在业务代码中
- 金额统一使用最小货币单位整数，避免使用 `float`
- 时间统一使用标准时间类型或 Unix 时间戳，项目内保持一致

#### 禁止

- 禁止字段名使用 `data1`、`type1`、`status2`
- 禁止金额字段使用 `float32`、`float64`
- 禁止把多个业务含义塞进一个文本字段中通过分隔符硬解析

#### 推荐

- 对身份证号、银行卡号、手机号等敏感字段，增加脱敏展示字段
- 对状态、类型、来源等字段配套常量或枚举定义

## 6. Handler 规范

### 6.1 BFF Handler

#### 必须

- 只负责协议解析、参数校验、登录态识别、调用下游、统一输出
- 必须从上下文中获取司机身份信息，不能信任前端直接上传的司机 ID
- 对外返回结构保持统一，错误码与错误消息符合约定

#### 禁止

- 禁止在 BFF Handler 中编写数据库查询
- 禁止在 BFF Handler 中复制 `srvDriver` 的核心业务规则
- 禁止直接把下游错误原文暴露给前端

#### 推荐

- 将重复参数校验逻辑下沉到公共校验函数
- 对聚合接口，显式标注调用了哪些下游能力

### 6.2 srvDriver Handler

#### 必须

- 只处理协议层转换、基础参数校验、调用 service
- 必须将 `context.Context` 透传到下游 service 与 repository

#### 禁止

- 禁止在 Handler 中写复杂分支业务
- 禁止在 Handler 中处理事务提交与回滚

## 7. Service 规范

### 必须

- Service 是核心业务规则唯一承载层
- 业务状态流转必须集中在 Service 中实现
- 涉及多个 repository 更新时，事务必须由 Service 控制
- Service 方法必须显式返回业务错误，不能仅依赖日志表达失败

### 禁止

- 禁止在 Service 中直接依赖 HTTP 框架对象
- 禁止在 Service 中直接依赖 Gin Context
- 禁止在 Service 中拼接面向前端的文案

### 推荐

- 每个业务动作对应一个清晰方法，不要把多个动作塞入一个超大函数
- 对复杂流程拆成小步骤私有方法，例如参数准备、状态检查、数据写入、事件记录
- Service 中优先使用早返回减少嵌套

## 8. Repository 规范

### 必须

- Repository 负责封装数据库访问细节
- 查询条件、排序、分页规则必须可读，必要时提取查询对象
- 数据更新必须明确受影响条件，防止误更新全表

### 禁止

- 禁止在 repository 中写业务审批、资格判断、展示拼装逻辑
- 禁止无条件更新
- 禁止把数据库错误吞掉后返回空结果

### 推荐

- 一个 repository 文件聚焦一个业务域
- 对复合查询提供专门方法，不要让上层自己拼条件
- 对常用查询补充索引关注点说明

## 9. 错误码规范

### 必须

- 错误码必须分层管理，区分系统错误、参数错误、业务错误
- 同一业务域必须维护稳定的错误码语义
- 前端可感知的错误必须有明确、稳定、可回归测试的错误码

建议错误码分类：

- `0`：成功
- `4xxxx`：参数与请求错误
- `5xxxx`：业务规则错误
- `6xxxx`：依赖服务错误
- `9xxxx`：系统内部错误

### 禁止

- 禁止直接返回数据库错误字符串
- 禁止不同业务场景复用同一个模糊错误码
- 禁止只返回 `"失败"`、`"系统异常"` 而无可追踪编码

### 推荐

- 建立 `code -> message -> 场景说明` 的映射
- 对个人中心重点场景单独定义错误码，如实名认证中、银行卡已绑定、提现条件不足等

## 10. 日志规范

### 必须

- 使用结构化日志
- 每条错误日志至少包含 `trace_id`、接口名、核心业务标识、错误对象
- 日志中必须区分正常业务拒绝和系统异常
- 敏感信息必须脱敏后输出

### 禁止

- 禁止打印身份证号、银行卡全号、手机号全号、验证码、密码、token
- 禁止使用 `fmt.Println` 代替正式日志
- 禁止同一错误被多层重复打印导致日志污染

### 推荐

- BFF 与 srvDriver 都记录统一链路标识
- 关键状态流转增加审计日志，如提交认证、审核通过、绑卡、解绑、提现申请

## 11. 配置规范

### 必须

- 配置项统一集中管理，禁止在代码中硬编码环境差异值
- 配置结构体字段要与配置文件键保持清晰映射
- 超时、重试、连接地址、密钥引用必须配置化

### 禁止

- 禁止把密钥、账号、数据库地址直接写入代码仓库
- 禁止业务代码中散落读取环境变量逻辑

### 推荐

- 为配置项补充默认值说明和生效范围说明
- 对关键配置启动时做校验并尽早失败

## 12. Context 与超时规范

### 必须

- 所有跨层方法必须显式传递 `context.Context`
- 下游 RPC、数据库调用必须设置合理超时
- 从入口提取 `trace_id`、`driver_id` 等链路信息并透传

### 禁止

- 禁止在底层自行创建背景 context 替代上游 context
- 禁止忽略 context 取消信号

### 推荐

- 对慢查询、慢 RPC 统一打点
- 对重试逻辑配合 context 截止时间控制总耗时

## 13. 事务规范

### 必须

- 事务只能在 Service 层开启
- 一个事务只包裹强一致性必须的数据操作
- 事务代码必须清晰标识开始条件、提交条件、回滚条件

### 禁止

- 禁止把外部 RPC 调用长时间包裹在数据库事务中
- 禁止为“保险”给所有写操作无差别加事务

### 推荐

- 将事务内外逻辑分离，缩小事务范围
- 对失败补偿型流程采用异步事件或状态驱动方式设计

## 14. Proto 与 RPC 规范

### 必须

- proto message 命名必须体现领域语义
- 一个 RPC 方法只表达一个清晰业务动作
- proto 字段变更必须遵守兼容原则，不随意复用已废弃字段号

### 禁止

- 禁止在一个 RPC 中混合多个独立业务动作
- 禁止使用含糊 message 名称，如 `CommonRequest`、`ResultData`

### 推荐

- 个人中心相关 proto 按域拆分：`profile`、`verify`、`wallet`、`bankcard`
- 为关键字段添加注释，说明含义、单位、状态取值

## 15. 测试规范

### 必须

- 新增业务规则必须有测试覆盖
- Service 层必须作为测试重点
- 涉及状态流转、金额计算、资格校验、脱敏规则的逻辑必须覆盖边界场景

### 禁止

- 禁止仅依赖手工联调替代自动化测试
- 禁止只测成功路径不测失败路径

### 推荐

- Repository 层可结合测试库或桩进行验证
- Handler 层至少覆盖参数校验、错误映射、返回结构
- 为典型场景建立表驱动测试

## 16. 重构治理规范

### 必须

- 新代码必须完全遵守本文档
- 触达存量代码时，至少完成“顺手整改”，包括命名修正、错误透传修正、日志脱敏修正、明显职责越层修正
- 涉及大文件修改时，应优先按业务域拆分而不是继续堆积

### 禁止

- 禁止以“历史代码就是这样”为理由复制旧问题到新代码
- 禁止在重构名义下做无边界的大面积无关改动

### 推荐

- 按“高频变更优先、事故高发优先、个人中心核心链路优先”治理存量代码
- 对暂时无法彻底整改的代码，补充 TODO 与整改计划，不允许沉默放过

## 17. 代码评审清单

### 必须检查

- 是否存在跨层职责污染
- 是否存在司机 ID 从前端透传而非鉴权上下文获取
- 是否存在未脱敏日志
- 是否存在错误码缺失或错误语义不清
- 是否存在金额、状态、时间字段设计不规范
- 是否存在事务边界不清或 RPC 与事务混用
- 是否存在只改功能不补测试

### 禁止放行

- 明显破坏分层边界
- 新增魔法数字、硬编码状态值、硬编码配置
- 直接返回内部错误细节给前端
- 直接复用旧的坏模式扩散到新模块

### 推荐关注

- 代码是否足够表达业务意图
- 命名是否能让新同学快速理解
- 是否为后续扩展预留清晰边界

## 18. 建议的新增代码模板

以个人中心新能力为例，建议最小落地单元如下：

1. BFF 新增路由与 handler
2. BFF 调用对应 rpc client
3. srvDriver 新增 handler 方法
4. srvDriver 新增 service 方法
5. srvDriver 新增 repository 方法
6. 补充错误码、日志埋点、测试

任何能力开发都应先明确它属于哪个业务域，再落到对应分层，不允许先写功能再补结构。
