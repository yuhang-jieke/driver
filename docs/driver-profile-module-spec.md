# 司机端个人中心模块规范

## 1. 适用范围

本文档是 [go-driver-dev-spec.md](D:/software/GoWork/src/driver/docs/go-driver-dev-spec.md) 在司机端个人中心场景下的专题补充，适用于以下能力：

- 司机基础资料
- 头像与图片上传
- 实名认证与资料审核
- 银行卡管理
- 钱包信息与提现相关能力
- 个人中心首页信息聚合

如与总规范冲突，以"更严格者"为准。

## 2. 领域划分

司机端个人中心按以下子域拆分：

1. `profile`：基础资料、头像、联系信息展示、司机标签
2. `verify`：实名认证、证件提交、审核状态、审核原因
3. `bankcard`：绑卡、换卡、解绑、银行卡列表与默认卡
4. `wallet`：钱包余额、冻结金额、收入汇总、提现资格、提现页规则
5. `upload`：图片上传、文件校验、文件地址回传
6. `home`：个人中心首页聚合信息

### 必须

- 每个子域必须有明确 owner 与边界
- 新接口必须先归属到子域，再设计目录与方法
- 一个 Service 文件可包含同一子域多个方法，但不能横跨多个无关子域

### 禁止

- 禁止继续增加 `crud` 式无语义聚合入口承接个人中心能力
- 禁止把认证、钱包、绑卡混写在一个"万能个人中心服务"中

### 推荐

- 后续逐步将现有代码按子域拆文件
- 首页聚合逻辑作为单独子域管理，不直接堆在资料服务中

## 3. 目录落地约束

结合当前工程，建议如下：

### `taketaxi/bffDriver/internal/handler`

#### 必须

- 按子域拆分 handler 文件，如 `profileHandler.go`、`walletHandler.go`
- 聚合接口可单独使用 `homeHandler.go`

#### 禁止

- 禁止继续在一个 handler 文件中堆积全部个人中心接口

### `taketaxi/bffDriver/internal/rpcClient`

#### 必须

- 对每个下游域能力提供明确方法封装
- RPC 调用方法名必须与下游业务动作一致

### `taketaxi/srvDriver/internal/handler`

#### 必须

- 一个 handler 文件聚焦一个业务域
- 当前 `crudHandler.go` 新能力禁止继续进入，后续只减不增

### `taketaxi/srvDriver/internal/service`

#### 必须

- 以 `profileService.go`、`verifyService.go`、`walletService.go`、`bankCardService.go` 为主要承载
- 每个文件负责对应子域业务，不跨域写入核心规则

### `taketaxi/srvDriver/internal/repository`

#### 必须

- 一个 repository 文件只聚焦一个子域表或一组强相关表
- 查询方法命名体现业务语义，不允许 `GetInfo`、`UpdateData`

## 4. BFF 与 srvDriver 职责边界

### 4.1 BFF 职责

#### 必须

- 负责登录态识别与司机上下文提取
- 负责 HTTP 入参校验与前端语义转换
- 负责聚合多个下游结果，输出端侧所需结构
- 负责统一脱敏展示，例如手机号、身份证号、银行卡尾号展示

#### 禁止

- 禁止在 BFF 决定实名认证是否可提交、是否可提现等核心业务规则
- 禁止 BFF 自己拼接数据库读写逻辑

### 4.2 srvDriver 职责

#### 必须

- 负责个人中心核心业务规则
- 负责状态流转、幂等控制、事务与持久化一致性
- 负责对外暴露稳定的业务语义

#### 禁止

- 禁止 srvDriver 直接依赖前端页面字段命名
- 禁止把展示用文案作为核心返回的一部分硬编码在 service 中

## 5. 司机身份与鉴权规则

### 必须

- 司机身份以鉴权上下文中的 `driver_id` 为准
- 所有个人中心写操作必须校验当前操作人与数据归属一致
- 查询接口如允许代查，必须显式定义场景与权限来源

### 禁止

- 禁止信任前端直接传来的 `driver_id`
- 禁止使用 URL 参数中的司机 ID 直接查询个人中心敏感信息

### 推荐

- 将司机上下文封装成统一上下文对象，避免每层重复解析

## 6. 接口设计规范

### 6.1 查询接口

#### 必须

- 查询接口返回结构必须稳定，字段命名统一
- 对敏感信息返回展示值时必须脱敏
- 对状态字段必须返回机器可识别值，必要时再补充展示文本

#### 禁止

- 禁止只返回中文状态文案、不返回状态码
- 禁止前后端自行猜测字段是否为空代表某种状态

### 6.2 提交与修改接口

#### 必须

- 必须校验当前状态下是否允许修改
- 必须明确幂等语义，例如重复提交认证资料如何处理
- 对关键写操作必须记录操作日志

#### 禁止

- 禁止"无脑覆盖"已审核通过的重要资料
- 禁止跳过状态校验直接更新认证、绑卡、提现类数据

### 6.3 聚合接口

#### 必须

- 聚合接口必须明确数据来源和降级策略
- 某个下游失败时必须定义返回策略：整体失败、局部降级或默认值回退

#### 禁止

- 禁止在聚合接口里悄悄吞掉关键失败导致页面展示错误状态

## 7. 个人资料子域规范

### 必须

- 基础资料与认证资料分开维护，不混用字段
- 头像、昵称、联系方式等可编辑资料必须定义可修改范围
- 更新资料前必须校验司机状态是否允许修改

### 禁止

- 禁止把审核态字段与展示态字段混在一个状态字段里
- 禁止基础资料更新接口顺带修改认证核心字段

### 推荐

- 将司机首页展示信息与基础资料详情拆成不同查询方法

## 8. 实名认证子域规范

### 必须

- 认证状态必须明确定义，例如 `INIT`、`SUBMITTED`、`REVIEWING`、`APPROVED`、`REJECTED`
- 每次状态变更必须有来源、时间、操作记录
- 驳回原因必须结构化存储或统一管理，不允许散落在多个文本字段
- 重复提交必须定义规则，例如审核中禁止重复提交，驳回后允许重新提交

### 禁止

- 禁止使用 `0/1/2` 裸数字直接在业务代码中判断认证流程
- 禁止认证通过后仍允许被普通资料更新接口覆盖关键实名信息

### 推荐

- 对认证流程抽象状态机或至少集中枚举定义
- 为审核链路补充审计日志与测试用例

## 9. 银行卡子域规范

### 必须

- 银行卡号存储、传输、日志打印都必须遵守脱敏与安全要求
- 默认卡规则必须唯一且可验证
- 绑卡、换卡、解绑必须校验司机身份与账户状态

### 禁止

- 禁止返回银行卡全号
- 禁止在接口层用字符串截取临时实现所有银行卡规则而不下沉统一逻辑

### 推荐

- 返回字段统一为 `bank_name`、`card_last4`、`is_default`
- 绑定结果增加可观测日志，便于排查用户投诉

## 10. 钱包子域规范

### 必须

- 金额字段统一使用分
- 可提现金额、冻结金额、总收入、待结算金额必须语义明确
- 钱包查询与提现资格校验必须分开建模，避免"一个接口返回所有业务判断"
- 新增提现页查询接口 `GetWithdrawPage`，提现页规则统一由 srvDriver 输出
- 提现页渲染与提现提交共用同一条资格校验路径（evaluateWithdrawEligibility），保证页态与提交态一致

### 禁止

- 禁止把金额直接转浮点后再参与比较
- 禁止把钱包展示金额和结算核心金额共用一个不清晰字段

### 推荐

- 资格校验结果返回明确失败原因码
- 金额展示格式化在 BFF 或前端进行，srvDriver 返回标准值

## 11. 上传子域规范

### 必须

- 上传前必须校验文件类型、大小、用途
- 上传结果必须返回稳定可追踪的文件标识
- 认证类图片与普通头像图片用途必须区分

### 禁止

- 禁止只根据文件后缀判断安全性
- 禁止把上传成功即视为认证资料已生效

### 推荐

- 上传完成后记录用途与归属对象，便于后续清理与追踪

## 12. 状态、枚举与常量规范

### 必须

- 个人中心相关状态、类型、来源必须集中定义
- 枚举值必须有业务注释
- 跨层共享枚举时必须保证语义一致

### 禁止

- 禁止在多个文件中重复定义同义不同名状态
- 禁止在代码里直接比较散落的字符串字面量

### 推荐

- 以域为单位维护常量文件，如 `profile_status.go`、`verify_status.go`

## 13. 错误码专题规范

个人中心建议至少覆盖以下错误类型：

- 参数非法
- 司机不存在
- 司机状态不允许操作
- 实名认证审核中
- 实名认证未通过
- 银行卡已绑定
- 默认卡不存在
- 钱包账户不存在
- 可提现金额不足
- 上传文件不合法

### 必须

- 每个高频用户可感知失败都要有稳定错误码
- 同一错误码不能跨子域表示不同含义

### 禁止

- 禁止把所有个人中心失败都折叠成"操作失败"

## 14. 日志与审计规范

### 必须

- 认证提交、审核结果、绑卡、解绑、提现申请、资料修改必须有审计日志
- 审计日志至少包含 `driver_id`、动作、结果、时间、请求链路标识

### 禁止

- 禁止把敏感原文直接打入日志

### 推荐

- 区分操作日志和错误日志，避免审计信息被错误日志淹没

## 15. 测试规范

### 必须

- 个人中心每个子域至少覆盖成功、状态不允许、数据不存在三个基础场景
- 认证、钱包、绑卡必须覆盖边界场景和重复提交场景
- 脱敏逻辑必须有单测

### 禁止

- 禁止只测"happy path"

### 推荐

- 对认证状态流转使用表驱动测试
- 对聚合接口增加下游异常降级测试

## 16. 存量代码治理规则

### 16.1 当前代码治理方向

基于当前目录结构，重点治理以下问题：

1. `crudHandler.go`、`crudService.go` 这类泛化命名文件逐步退出个人中心新需求承载
2. `handler` 过厚的问题逐步下沉到 `service`
3. 资料、认证、钱包、银行卡逻辑进一步按子域收敛
4. 返回结构、错误码、日志字段统一

### 16.2 治理分级

#### 必须

- 新增功能不得进入 `crud*` 泛化文件
- 修改高风险链路时，必须同步补充错误码和日志脱敏
- 触达个人中心核心链路时，发现明显越层逻辑必须整改

#### 禁止

- 禁止继续复制旧代码中的"大而全 handler/service"模式
- 禁止为了兼容历史写法而放弃新规范

#### 推荐

- 以业务域为单位做小步重构，不做一次性大爆炸迁移
- 每次需求开发顺带抽取 1 到 2 个重复逻辑到清晰边界中

## 17. 新增接口落地模板

以"更新司机头像"为例，标准流程应为：

1. `bffDriver` 定义 HTTP 入参与返回结构
2. `bffDriver` 从登录态上下文获取 `driver_id`
3. `bffDriver` 调用 `rpcClient.UpdateDriverAvatar`
4. `srvDriver/handler` 做协议转换与基础校验
5. `srvDriver/service` 校验司机状态、文件合法性、修改权限
6. `srvDriver/repository` 更新资料表
7. 记录操作日志
8. 返回统一错误码与响应
9. 补充单测

任何个人中心新接口都应遵守这个分层套路，不允许跳层开发。
